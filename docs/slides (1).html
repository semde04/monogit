Campus lost-and-found · Flutter, TypeScript and MongoDB

The problem

Lost property creates a coordination problem — and a privacy problem.

The finder

“Who should I give it to?”

There is no reliable way to match an item with its owner without posting personal details publicly.

The owner

“Where should I look?”

Announcements get scattered across class chats, and useful details are hard to search later.

Design goal: make the handover verifiable while keeping proof and conversation private.

The product

One campus service, two kinds of users.

Student · finder or claimant

Recover an item without public contact details.

Sign up with a campus matricule, post a lost or found item, answer a private proof question, then chat and confirm the handover.

Administrator

Keep the campus space trustworthy.

Review activity, remove or restore posts, suspend or reactivate accounts with a reason, and monitor service statistics.

Mobile app: Flutter + BLoC
Admin portal: Flutter Web
One shared REST API

The recovery journey

A claim becomes a handover only after both people confirm.

01

Post

Describe a lost or found item, its location and an optional photo.

02

Prove

The claimant answers a detail only the owner should know.

03

Accept

The finder reviews the answer. A private chat opens after acceptance.

04

Meet

The two participants arrange the handover in the claim conversation.

05

Confirm

Both confirm. The post closes and a return record is saved.

Push notifications keep participants informed about new claims, decisions and return confirmations.

Security & privacy

Authorization is checked on every protected action.

ThreatControl in the implementation
BOLA / ID guessingOwner and claim-participant checks run in API services; unrelated users cannot close posts or read chats.
Proof disclosurePublic item detail omits the proof question; the claimant’s answer is visible to the claim participants.
Stolen refresh tokenRefresh tokens are stored hashed and rotated; reuse revokes the user’s active sessions.
Weak credentialsPasswords use Argon2id; access JWTs expire after 15 minutes.
Abuse / oversized dataRate limiting, Zod validation, capped pagination and an 800 KB image limit.

The mobile app never receives database credentials.

A handover with accountability

An accepted claim is not yet a returned item.

Confirmation 1

The finder confirms the handover.

The item stays open until the other participant confirms too.

+

Confirmation 2

The claimant confirms receipt.

Only the two people in the accepted claim can confirm.

→

Saved return record

Both confirmations close the listing.

A receipt stores the item, finder, recipient and confirmation time. The event is added to the activity log.

The workflow avoids closing a post after only one person says the handover happened.

Trade-offs & next steps

We chose a working campus flow and know where to scale next.

Images

Simple storage today

Images are stored as base64 and capped at 800 KB. Next: object storage with signed URLs.

Search

Right-sized for the demo

Regex search is easy to deploy. Next: dedicated indexes or full-text search for larger datasets.

Notifications

Service credentials required

Push depends on valid Firebase installation tokens and server credentials configured outside Git.

Current strengths: reversible admin actions, audit history, bounded pagination and two-person return confirmation.
